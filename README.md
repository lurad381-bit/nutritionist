# Nutritionist: оценка блюда по ингредиентам

Это проект с трека Data Science в Школе 21. Формально он был командный, на двоих, я был тимлидом, но всё, что описано ниже, делал я: подготовку данных, модели, пищевую ценность, поиск похожих рецептов и саму программу.

Это консольная программа: вводишь список ингредиентов, а она предсказывает, насколько хорошим получится блюдо (bad / so-so / great), показывает пищевую ценность ингредиентов и подбирает 3 похожих рецепта.

```
$ python3 nutritionist.py milk, honey, jam
```

Данные это датасет [Epicurious](https://www.kaggle.com/datasets/hugodarwood/epirecipes) с Kaggle, там около 20 тысяч рецептов с рейтингом и 674 бинарными тегами.

**Подготовка данных.** Среди 674 тегов были не только ингредиенты, но и праздники, города, способы готовки и всякое такое. Чтобы отделить настоящие ингредиенты, я сверился с полным текстом рецептов и добавил ручной список исключений, в итоге осталось 341 признак. Ещё нашёл испорченную кодировку в названиях столбцов (типа `bon appÃ©tit`), из-за которой одни и те же теги дублировались, и исправил её.

**Регрессия.** Сначала пробовал предсказывать сам рейтинг. Сравнил 6 регрессоров (линейная регрессия, дерево, kNN, случайный лес, градиентный бустинг, Extra Trees) с подбором гиперпараметров через GridSearchCV на 5-фолдовой кросс-валидации. Лучшим оказался градиентный бустинг, но у него RMSE 1,26 против 1,31 у наивной модели, то есть по одним ингредиентам рейтинг предсказывается слабо.

**Классификация bad / so-so / great.** Классы сильно несбалансированы, great это 79 % рецептов, поэтому в моделях, которые это поддерживают (логистическая регрессия, дерево, случайный лес, Extra Trees), я использовал `class_weight='balanced'`, иначе модель почти всегда отвечает great. Метрику выбирал под цену ошибки: хуже всего назвать плохое блюдо отличным, поэтому важна precision класса great, и модели подбирал именно по ней, а не по accuracy. Итоговая модель это случайный лес в `sklearn.Pipeline`, precision класса great на тесте 0,85 при доле класса 0,79. Цена за это accuracy 0,67, она ниже, чем у наивной модели (0,79), потому что модель осторожнее называет блюдо отличным и чаще ошибается в другую сторону.

**Пищевая ценность и похожие рецепты.** Пищевую ценность ингредиентов брал из API [USDA FoodData Central](https://fdc.nal.usda.gov/api-guide.html) и пересчитывал в процент от суточной нормы. Похожие рецепты ищутся по мере Жаккара между наборами ингредиентов, то есть по доле общих ингредиентов среди всех ингредиентов двух рецептов.

**Что заметил и не успел исправить.** В собранной таблице пищевой ценности заполнились только белок, холестерин и часть витаминов группы B, а 25 нутриентов из 35 остались пустыми, в том числе жиры, углеводы, натрий, кальций и железо. Причина в том, что код ищет нутриенты по точному совпадению названия, а USDA API многие из них называет по-другому, например `Total lipid (fat)` вместо `Fat` или `Calcium, Ca` вместо `Calcium`. По-хорошему нужно сопоставить названия USDA с моими через таблицу соответствий, это первое, что стоит доделать.

**Как запустить:**
1. Скачать `epi_r.csv` и `full_format_recipes.json` с Kaggle и положить в папку `data/`.
2. Получить бесплатный ключ USDA API и задать его в переменной окружения: `export USDA_API_KEY=...`
3. `pip install -r requirements.txt`
4. Запустить `recipes.ipynb`, он обучит модель и создаст рядом `model.pkl`, `model_columns.pkl`, `nutrition_facts.csv` и `recipes_similarity.csv`.
5. `python3 nutritionist.py milk, honey, jam`

Данные и обученная модель в репозиторий не входят.

**Стек:** Python, pandas, NumPy, scikit-learn, requests, Jupyter
